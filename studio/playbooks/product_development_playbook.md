# Purpose

This playbook defines the Studio's standard workflow for developing products.

Every product, regardless of category or technology, follows the same development lifecycle.

The objective is to produce products that are practical, reliable, maintainable and professionally presented.

---

# Guiding Principles

Every product should:

* solve one primary problem exceptionally well
* remain simple to use
* hide unnecessary complexity
* be modular
* be easy to maintain
* be trusted by users

Features should support the product vision rather than expand it unnecessarily.

---

# Product Lifecycle

Every product progresses through the following stages.

```text
Idea

↓

Research

↓

Requirements

↓

Planning

↓

Design

↓

Development

↓

Internal QA

↓

Packaging

↓

Release Candidate

↓

Public Release

↓

Maintenance

↓

Iteration
```

Stages should be completed in sequence.

Do not skip stages without documented justification.

---

# Stage 1 - Idea

Objective:

Identify a genuine problem worth solving.

Questions:

* Who experiences this problem?
* Why does it matter?
* Is there an existing solution?
* Can the Studio create a meaningfully better solution?

Deliverables:

* Initial product concept
* GitHub Issue
* Product category

---

# Stage 2 - Research

Objective:

Understand the operational problem before proposing solutions.

Research should include:

* current workflows
* user behaviour
* existing tools
* constraints
* opportunities

Deliverables:

* Research Summary
* Key Findings
* Recommendations

---

# Stage 3 - Requirements

Objective:

Define exactly what Version 1 will achieve.

Requirements should distinguish between:

Included

Excluded

Future Considerations

Deliverables:

* Completed Product Template
* Defined success criteria
* Approved scope

---

# Stage 4 - Planning

Objective:

Break the product into manageable modules.

Planning should define:

* architecture
* modules
* workflows
* dependencies
* milestones
* GitHub Issues

Deliverables:

* Development plan
* Project board updated
* Module breakdown

---

# Stage 5 - Design

Objective:

Design the user experience before implementation.

Consider:

* navigation
* layout
* data flow
* reports
* dashboards
* spreadsheet structure

Design should follow the Studio Design System.

Deliverables:

* Wireframes (where appropriate)
* Layout plan
* Navigation structure

---

# Stage 6 - Development

Objective:

Build the product according to the approved plan.

Development should prioritise:

* correctness
* simplicity
* maintainability
* readability
* modularity

Work should be tracked through GitHub Issues.

---

# Stage 7 - Internal QA

Objective:

Verify that the product works as intended.

Testing should include:

* calculations
* workflows
* edge cases
* usability
* compatibility

Document all findings.

Critical issues should be resolved before proceeding.

---

# Stage 8 - Packaging

Objective:

Prepare the product for public distribution.

Packaging may include:

* spreadsheet
* documentation
* screenshots
* demo data
* licence
* release notes
* tutorial video

The package should feel complete and professional.

---

# Stage 9 - Release Candidate

Objective:

Conduct a final review.

Review should confirm:

* functionality
* documentation
* presentation
* compatibility
* Release Standards compliance

The Studio Director determines whether the product proceeds to release.

---

# Stage 10 - Public Release

Objective:

Publish the product.

Possible distribution channels include:

* Selar or another approved checkout platform
* GitHub Releases
* Studio website
* Direct client delivery

Every release should include:

* version number
* release notes
* changelog

---

# Stage 11 - Maintenance

Objective:

Support released products.

Maintenance includes:

* bug fixes
* documentation updates
* compatibility improvements
* customer support
* issue triage

Released products remain active Studio assets.

---

# Stage 12 - Iteration

Objective:

Improve products based on evidence.

Inputs may include:

* user feedback
* bug reports
* feature requests
* usage data
* customisation projects

New features should only be added when they strengthen the product.

---

# Modularity

Products should be built from reusable modules.

Whenever practical:

* reuse existing components
* avoid duplication
* isolate responsibilities

Modules should remain independently understandable.

---

# AI Collaboration

AI contributors may assist during every stage.

However:

* humans approve direction
* humans validate outputs
* humans approve releases

AI accelerates development.

Humans remain accountable.

---

# Definition of Ready

Development begins only when:

* research completed
* requirements approved
* scope defined
* GitHub Issues created
* product architecture planned

Beginning implementation before planning is discouraged.

---

# Definition of Done

A product stage is complete when:

* deliverables completed
* documentation updated
* GitHub Issues resolved
* review performed
* quality standards satisfied

---

# Product Metrics

Every product should monitor:

* downloads
* active users
* bug reports
* feature requests
* customisation enquiries
* customer feedback

These metrics guide future development.

# Closing Statement

Great products are rarely the result of isolated moments of inspiration.

They emerge from disciplined, repeatable development processes that prioritise solving real problems, maintaining high quality and continuously learning from users.

This playbook exists to make that process consistent across every Studio product.
