# Purpose

This document establishes the official language of the Studio.

Every contributor, whether human or AI, must use the terminology defined here.

A term has exactly one meaning within the Studio.

If uncertainty exists, this document is the authority.

---

# Vocabulary Principles

The Studio values precision.

Every important concept should have:

* one name
* one definition
* one intended use

Avoid creating synonyms for established terms.

Consistency improves communication, documentation and software quality.

---

# Studio

The complete engineering organisation responsible for creating and maintaining products.

The Studio includes:

* documentation
* standards
* products
* shared assets
* workflows
* AI contributors
* human contributors

The Studio is not a product.

---

# Category

A major area of work containing related products.

Current categories are:

* Sports Competitions
* Sports Businesses
* Sports Performance & Sports Science
* Personal Systems

Categories organise products.

They do not contain implementation logic.

---

# Product

A complete operational system designed to solve one primary problem for one primary user.

Every product must have:

* clear purpose
* defined scope
* documentation
* version history
* lifecycle

Examples:

Competition Manager

Running Log

Gym Reporting System

---

# Product Family

A collection of closely related products that share modules, design language or purpose.

Example:

Competition Manager

Competition Dashboard

Competition Reporting

Competition Registration

These form one product family.

---

# Module

The primary functional building block of a product.

Modules perform one major responsibility.

Modules should be reusable whenever practical.

Examples:

Registration Module

Standings Module

Results Module

Attendance Module

Reporting Module

A module may be used by multiple products.

---

# Feature

A specific capability provided by a module.

Examples:

Automatic league standings

QR code registration

Export to PDF

Attendance summary

A feature belongs to one module.

Features should never exist independently.

---

# Workflow

The sequence of actions taken to complete a task.

Examples:

Player Registration Workflow

Competition Setup Workflow

Monthly Reporting Workflow

A workflow describes behaviour.

It is not software.

---

# Template

A reusable starting point.

Templates reduce repeated work.

Examples:

Spreadsheet Template

Report Template

Dashboard Template

Documentation Template

Templates are reusable assets.

---

# Asset

Any reusable file supporting the Studio.

Examples:

Icons

Brand graphics

Images

Example datasets

Colour palettes

Assets are shared wherever practical.

---

# Component

A reusable interface element.

Components are primarily used in software or documentation.

Examples:

Header

Navigation

Card

Table

Button

Components belong to interfaces.

They are **not** modules.

---

# System

A collection of modules working together to solve an operational problem.

Every product is a system.

Not every system becomes a product.

---

# User

A person using a released product.

Examples:

Coach

Competition organiser

Gym owner

Analyst

Runner

Administrator

---

# Customer

A user or organisation that purchases, licenses or commissions work.

All customers are users.

Not all users are customers.

---

# Client

An organisation or individual receiving customised work from the Studio.

Clients receive services beyond the standard product.

Examples:

Custom dashboards

Tailored reports

Organisation-specific workflows

Consulting

---

# Release

A publicly available version of a product.

Every release should include:

* version number
* documentation
* changelog

---

# Version

A numbered state of a product.

Examples:

1.0.0

1.1.0

2.0.0

Versions communicate change.

---

# Patch

A release that fixes defects without adding significant functionality.

---

# Minor Version

A release introducing new features while maintaining compatibility.

---

# Major Version

A release introducing substantial changes.

Major versions may redesign products or introduce breaking changes.

---

# Prototype

The first working implementation of a product.

Purpose:

Validate ideas.

Not intended for public release.

---

# Release Candidate

A product believed to be ready for release pending final review.

---

# Public Release

A product approved by the Studio Director and made available to users.

---

# Backlog

A prioritised collection of future work.

Examples:

Feature ideas

Improvements

Bug fixes

Research tasks

Items remain in the backlog until scheduled.

---

# Roadmap

A high-level plan describing future product direction.

Roadmaps communicate intent.

They do not guarantee delivery dates.

---

# Requirement

A capability that must exist for a product to achieve its objective.

Requirements define success.

They are not suggestions.

---

# Constraint

A limitation within which a product must operate.

Examples:

Google Sheets compatibility

Offline capability

Budget

Time

Target audience

Constraints shape design decisions.

---

# Standard

A mandatory rule governing Studio work.

Standards apply across all products.

Examples:

Documentation Standards

Design Standards

Release Standards

---

# Guideline

A recommended practice.

Guidelines allow professional judgement.

Unlike standards, they may have justified exceptions.

---

# Principle

A long-term belief defined by the Studio Charter.

Principles change rarely.

Every standard should support one or more principles.

---

# Documentation

Any written material supporting the Studio or its products.

Documentation includes:

* manuals
* user guides
* technical guides
* architecture
* requirements
* changelogs

Documentation is considered part of the product.

---

# Decision

A documented conclusion affecting the Studio or a product.

Important decisions should always be recorded.

Decisions should never rely on memory.

---

# Review

A structured evaluation of work before approval.

Reviews may assess:

* quality
* correctness
* usability
* consistency
* documentation

---

# Approval

Formal acceptance by the Studio Director.

Only approved work may progress to release.

---

# Deprecation

The process of preparing a product or feature for retirement.

Deprecated products remain usable but should not receive significant new development.

---

# Archive

A completed or retired item retained for historical purposes.

Archived work is not actively maintained.

---

# Deprecated Terms

The following terms should be avoided because they create ambiguity.

Instead of:

"Thing"

Use:

Module, Feature or Product.

---

Instead of:

"Dashboard"

Specify:

Reporting Dashboard

Performance Dashboard

Business Dashboard

Competition Dashboard

---

Instead of:

"Tracker"

Specify the operational purpose.

Examples:

Attendance Tracker

Running Log

Expense Tracker

Wellness Tracker

---

Instead of:

"System" (when referring to only one part)

Use:

Module

Feature

Workflow

or Product.

---

# Naming Philosophy

Names should be:

* descriptive
* concise
* professional
* durable

Avoid:

* trendy names
* unnecessary abbreviations
* internal jargon
* cleverness over clarity

If a name requires explanation, it should be reconsidered.

---

# Closing Statement

A shared language creates shared understanding.

By defining a consistent vocabulary, the Studio reduces ambiguity, improves communication and enables humans and AI to collaborate using the same mental model.

Every contributor should use these definitions consistently across documentation, software and discussion.
